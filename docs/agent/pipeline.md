# 协作工艺

与 `docs/design-overview-v2.md` 第 10 章同源，这里只留日常要照做的那几条。

## 六步流水线

规格 → 切片 → 契约 → 实现 → 自检 → 人审。跳过任何一步都会在合并后返工。

## 切片模板（缺哪段就打回）

```text
## 目标
一句话说清单一行为。
## 验收
可执行的验收项：哪个测试文件新增哪几条、哪张截图基准、要不要跑 campus-validate。
## 不做什么
明确列出本切片不许碰的目录与文件。
## 风险
一句话；没有就写「无」。
```

写不出验收脚本的需求不算想清楚，退回澄清，不许自行脑补实现方案。一个需求切 3–5 个切片，超出就重切。

## 门禁三色

- 绿：只碰本切片声明内的文件，测试全绿 → 可自动合。
- 黄：碰了相邻模块或改了共享类型 → 一人看过再合。
- 红：动了 `core/`、数据 schema、寻路算法、渲染主循环、部署与许可 → 全体评审。
人每天只看 3–8 个黄红条目，其余交给 CI。

## PR 纪律

- 一个切片一个 PR，标题写清切片编号；正文贴验收结果（本地或 CNB 构建链接）。
- 提交信息走 conventional commits，scope 用目录或模块名（`fix(editor):`、`feat(pack):`）。
- 不夹带格式化、不改无关文件；确实需要顺手修就单开一个 `chore` PR。
- 审查只回答三件事：对不对、越没越界、测够没测够。

## 开发通道（2026-11-18 定，2026-11-20 修订：CNB NPC 优先）

**第一原则：功能开发一律先由 CNB NPC 编排完成，本机不抢着写。**

派工流程（照做，顺序不能反）：

1. 先 `cnb` 上查有没有现成切片，别重复开。
2. 写 issue，四段齐：目标 / 范围（可改目录 + 明确不动什么）/ 验收（可粘贴命令与期望）/ 风险（回滚与依赖）。
3. 在 issue 里 `work_mode: true` 并 @CodeBuddy 或项目 NPC 派工，评论写清五条：分支名、改动目录白名单、自测命令、PR 标题前缀、越界处理（越界直接丢弃，不辩论）。
4. GitHub 侧只承担 PR 复核与 Pages 部署；分支与代码从 CNB 同步过来后合入 `main`。
5. 重活不占本机：web 侧构建与全量测试走 CNB 云原生构建/开发环境，Android 构建走 GitHub Actions。

本机（项目管家）只做四件事：

- 统筹与确认：维护切片索引、判门禁色、核对验收命令、在 PR 上给「可合 / 不行」结论。
- 本机验证：`npx tsc --noEmit`、`npm test`、`npm run build` 与 `verify:*` 脚本，作为放行前的独立复核。
- 记录：进度、决策、风险回写台账（`docs/agent/memory.md`）。
- 例外才自己动手：负责人当轮直接点的修补，或 NPC 迟迟不交付而负责人点头的抢修。例外必须在 PR 正文里写明「为什么没走 NPC」+ issue 号，否则视为违规。

## 提交身份（2026-11-20 定，同日修订：两个平台各用自家 noreply）

两个仓库 **同步同一份内容**：GitHub `mico-v/campus-nav-3d`（远程 `origin`）与 CNB `mico-v/campus-nav-3d`（远程 `cnb2`）。
平台各有自己的提交身份，**只认这两个地址，不许出现第三个**：

| 平台 | 提交作者 |
| --- | --- |
| GitHub | `mico-v <232133607+mico-v@users.noreply.github.com>` |
| CNB | `mico-v <300VF8hf4PTB0jXk8GkciD+cnb.mico-v@noreply.cnb.cool>` |

规矩：

- 在本机往 `origin` 提交，用 GitHub 那套（本仓库 `git config user.email` 就设它）。
- 往 CNB 提交时按下面命令临时带上，**不要改全局配置**：

```bash
git -c user.name='mico-v' \
    -c user.email='300VF8hf4PTB0jXk8GkciD+cnb.mico-v@noreply.cnb.cool' commit -m '...'
```

- 派出 NPC 干活时，在派工评论里写明 CNB 侧提交作者用上面那个地址。
- 严禁：个人邮箱、`kei-bot@users.noreply.github.com`、任何自建机器人地址。
- 发送前自检：

```bash
git config user.email                       # GitHub 侧：232133607+mico-v@users.noreply.github.com
git log -1 --format='%ae %ce'               # 与即将推送的平台一致
```

- 历史提交里的旧邮箱不改写；`git merge` 产生的 merge commit 由合并人身份决定，合并前先确认身份已切好。
- GitHub squash 合并时 committer 会被服务端替换成 `GitHub <noreply@github.com>`，这是平台行为，不算违规；作者仍是上表地址。

## 进度追踪（2026-11-18 定）

- 状态板：`npm run status`（`tools/project-status.mjs`）拉 CNB issue/PR、最近构建与提交，输出里程碑、在飞、派工中、停滞提醒四段。
- 判定口径：PR 超 4 小时无人动 → 等复核超时；派工 issue 超 24 小时无新评论 → 疑似停滞；同时在飞 PR 上限 3，超过就先排队再派工。
- 每合一片，先回写台账（`memory.md` 里程碑行 + 一条决策），再派下一片；台账没写等于没合。
- 汇报节奏：负责人要实时进度时，按「进展 / 卡点 / 待办 / 风险 + 一句结论」，只引用状态板、PR 与构建日志里看得到的事实。

## 规划口径

- 切片必须能在一个 PR 内完成，验收项要可执行（命令 + 期望输出）；写不出验收就是没想清楚，退回澄清。
- 一个需求拆 3–5 片并标依赖；被依赖的先合，依赖它的才派工。
- 派工信息固定五条：分支名、改动目录白名单、自测命令、PR 标题前缀、越界处理（复核时直接丢弃，不辩论）。
- 每片写「不做什么」；验收要有可粘贴的命令，不写「运行正常」这类不可核验的描述。

## 决策记录

重大取舍写成 ADR 放进 `docs/adr/`：背景、选项、结论、代价、复查条件。
没有 ADR 的架构级改动，项目管家记为「未决」并在下次汇报里点出来。
