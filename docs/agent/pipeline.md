# 协作工艺

与 `docs/design-overview-v2.md` 第 10 章同源，这里只留日常要照做的那几条。

## 六步流水线

规格 → 切片 → 契约 → 实现 → 自检 → 人审。跳过任何一步都会在合并后返工。

## 切片模板（缺哪段就打回）

```text
## 目标
一句话说清单一行为。
## 验收
可执行的验收项：哪个测试文件新增哪几条、哪张截图基准、要不要跑 campus-validate。
## 不做什么
明确列出本切片不许碰的目录与文件。
## 风险
一句话；没有就写「无」。
```

写不出验收脚本的需求不算想清楚，退回澄清，不许自行脑补实现方案。一个需求切 3–5 个切片，超出就重切。

## 门禁三色

- 绿：只碰本切片声明内的文件，测试全绿 → 可自动合。
- 黄：碰了相邻模块或改了共享类型 → 一人看过再合。
- 红：动了 `core/`、数据 schema、寻路算法、渲染主循环、部署与许可 → 全体评审。
人每天只看 3–8 个黄红条目，其余交给 CI。

## PR 纪律

- 一个切片一个 PR，标题写清切片编号；正文贴验收结果（本地或 CNB 构建链接）。
- 提交信息走 conventional commits，scope 用目录或模块名（`fix(editor):`、`feat(pack):`）。
- 不夹带格式化、不改无关文件；确实需要顺手修就单开一个 `chore` PR。
- 审查只回答三件事：对不对、越没越界、测够没测够。

## 开发通道（2026-11-18 定）

- 需求先落 **cnb.cool issue**（模板与门禁标签齐了才开工），在 issue 里 `work_mode: true` 并 @CodeBuddy 或项目 NPC，让它写代码、推分支、开 PR。
- GitHub 侧只承担 PR 评审与 Pages 部署；分支与代码从 CNB 同步过来后合入 `main`。
- 重活不占本机：web 侧构建与全量测试走 CNB 云原生构建/开发环境，Android 构建走 GitHub Actions。
- 项目管家负责确认与统筹：维护切片索引、判门禁色、核对验收命令、在 PR 上给「可合 / 不行」结论，并把长任务进度随时报给负责人。

## 进度追踪（2026-11-18 定）

- 状态板：`npm run status`（`tools/project-status.mjs`）拉 CNB issue/PR、最近构建与提交，输出里程碑、在飞、派工中、停滞提醒四段。
- 判定口径：PR 超 4 小时无人动 → 等复核超时；派工 issue 超 24 小时无新评论 → 疑似停滞；同时在飞 PR 上限 3，超过就先排队再派工。
- 每合一片，先回写台账（`memory.md` 里程碑行 + 一条决策），再派下一片；台账没写等于没合。
- 汇报节奏：负责人要实时进度时，按「进展 / 卡点 / 待办 / 风险 + 一句结论」，只引用状态板、PR 与构建日志里看得到的事实。

## 规划口径

- 切片必须能在一个 PR 内完成，验收项要可执行（命令 + 期望输出）；写不出验收就是没想清楚，退回澄清。
- 一个需求拆 3–5 片并标依赖；被依赖的先合，依赖它的才派工。
- 派工信息固定五条：分支名、改动目录白名单、自测命令、PR 标题前缀、越界处理（复核时直接丢弃，不辩论）。
- 每片写「不做什么」；验收要有可粘贴的命令，不写「运行正常」这类不可核验的描述。

## 决策记录

重大取舍写成 ADR 放进 `docs/adr/`：背景、选项、结论、代价、复查条件。
没有 ADR 的架构级改动，项目管家记为「未决」并在下次汇报里点出来。
