# 校园时空导航 · 总体设计方案 v2

版本 v2.0 · 2026-11-18 · 适用仓 `campus-nav-3d`（线上 map.mioc.cc）
本文分层书写：第一屏是给人看的结论，后面才是给实现看的细节。读到哪一层由你决定。

---

## 30 秒速览

- **一句话定位**：以「校园地点」为一切的锚点，做一套可复用的开源校园空间底座 —— 代码、数据规范、建模工具链一起开源，任何学校填数据就能上线。
- **三个交付物**：`campus pack` 数据规范（通用）＋ 3D/2D/室内一体的站点与 PWA（本校实例）＋ 地点级活动信息与深链导航（社交侧）。
- **从作品到底座**：原来的限制（大创周期、单一校区、只做展示）全部放开，目标改成「别人能 fork 走」。
- **地图要有三副脸**：3D 透视（默认）、2D 平面（看关系与全貌）、室内剖切（进楼之后）。
- **信息的单位是地点**：一条活动、一条通知都挂在具体房间/场地，分享出去就是一条能直接开始导航的链接。
- **UI 学 StuDev**：高信息密度、克制的状态色、时间刻度尺、深浅双主题、零装饰动效。
- **开发模式**：agent 主导编码，人只做方向评审与验收；验收全部脚本化，靠 CI 门禁说话。
- **本机只做编辑与单测**，构建、e2e、截图、打包一律上 GitHub Actions，产物回传本机做视觉验收。

一句话：把「导航工具」升级成「校园空间操作系统」，用 agent 的产能把它做完整。

## 1. 定位重写

### 1.1 三层交付物

**第一层：Campus Pack 规范（通用资产）**
一套 JSON Schema 描述任意校园：边界、分区、建筑体、楼层层、房间单元、室外路网、室内路网、POI、场地。配三个 CLI：`campus-import`（从 OSM / 平面图 / Blender 导）、`campus-validate`（校验拓扑与几何）、`campus-bundle`（产出可分发的离线包）。这一层是「开源可通用」的兑现物，也是别人 star 你的理由。

**第二层：站点与客户端（本校实例 + 可直接复用的前端）**
Vite + TypeScript + Three.js（3D）+ Canvas/SVG 或 MapLibre（2D），共享同一份视图状态与寻路内核。PWA 可安装、离线可用。编辑器页面让非程序员也能补楼、补房间、补路。

**第三层：地点级信息与活动（社交侧）**
任何地点都可以挂内容：社团活动、讲座、失物招领、临时施工、空教室。内容带时效，分享出去是一条能直接开始导航的链接。这一层决定「有人天天用」，前两层决定「有人愿意 fork」。

### 1.2 与同类项目的分界

| 能力 | StuDev（南邮） | room-tba（UPLB） | VIT-CampusMap | 本项目目标 |
|---|---|---|---|---|
| 课表 / 考务时间轴 | 强 | 中 | 无 | 不做（本校已有课表 bot，接口可接） |
| 3D 校园 | 强（Blender 129 栋） | 无 | 无 | 中强，重点在室内 |
| 2D 平面 | 弱 | 强 | 强（MapLibre） | 双模同源 |
| 室内导航 | 强（564 教室） | 弱 | 无 | 强，含跨楼跨层 |
| 地点级 UGC / 活动 | 无 | 无 | 无 | 差异化主战场 |
| 深链一键导航 | 部分 | 无 | 无 | 一等功能 |
| 多校可复用 | 单校 | 单校 | 单校 | 规范 + 导入器 |
| 离线优先 | 强 | 强 | 中 | 中强（离线包） |

结论：不在「课表联动」上硬碰 StuDev（那是它的主场且需要教务数据），把火力压在 **室内精度 + 地点级信息 + 深链 + 多校规范** 这四件没人同时做的事上。

### 1.3 成功判据

- 能跑：任意一台手机打开即用，首屏 3D 在 4G 下 3 秒内可交互。
- 能懂：从不看说明的人，30 秒内能找到一栋楼并开始走。
- 能传：一条活动链接发到群里，点开即定位、即导航。
- 能复用：第二个学校能在不改前端代码的前提下，只换数据上线。
- 能维护：三个人 + 若干 agent，用周末节奏持续供数据与功能。

## 2. 通用化：Campus Pack 规范

### 2.1 数据分层

| 层 | 内容 | 变化频率 | 存放 |
|---|---|---|---|
| L0 底图 | 边界、分区、水体、绿地、场地 | 极低 | 包内静态 |
| L1 建筑 | 体块、高度、轮廓、别名、类别 | 低 | 包内静态 |
| L2 室内 | 楼层层、房间单元、门位、楼梯电梯、室内路网 | 中 | 包内静态 |
| L3 动态 | 活动、通知、开放状态、临时封路 | 高 | 服务端 + 增量同步 |

前两层与第三层的数据量差距很大：静态包可以做到几百 KB，动态数据只有若干 KB 的 JSON，正好适合「静态站点 + 轻后端」。

### 2.2 schema 骨架

```jsonc
{
  "schema": "campus-pack/2",
  "id": "usts-tianping",
  "name": "苏州科技大学 · 天平校区",
  "crs": "local-meters",          // 原点 + 单位，或 wgs84
  "origin": { "lat": 31.29, "lng": 120.55, "rotation": 0 },
  "bounds": { "min": [-520, -410], "max": [520, 470] },
  "units": "meter",
  "zones":     [{ "id": "west-academic", "name": "西区教学", "polygon": [[x,y], ...] }],
  "buildings": [{
    "id": "b-lib",
    "name": "图书馆",
    "aliases": ["图书信息中心", "LIB"],
    "category": "library",
    "footprint": [[x,y], ...],
    "height": 24,
    "levels": [
      { "index": 1, "name": "1F", "elevation": 0, "height": 4.5,
        "outline": [[x,y], ...],
        "units": [
          { "id": "r-101", "name": "自习室 A", "polygon": [[x,y], ...],
            "capacity": 80, "type": "study", "tags": ["quiet", "socket"] }
        ],
        "portals": [ { "id": "door-1", "kind": "door", "at": [x,y], "to": "outdoor" } ],
        "verticals": [ { "id": "st-a", "kind": "stairs", "at": [x,y], "to": 2 } ]
      }
    ]
  }],
  "roadNetwork": { "nodes": [{ "id": "n1", "at": [x,y] }], "edges": [{ "from": "n1", "to": "n2", "cost": 12 }] },
  "indoorNetwork": { "nodes": [{ "id": "i1", "at": [x,y], "level": 3, "building": "b-lib" }], "edges": [] },
  "pois": [{ "id": "p-1", "name": "一食堂", "at": [x,y], "level": 0, "building": null, "tags": ["food"] }]
}
```

设计取舍三条：

1. **房间是「层上的多边形」而不是盒子**。渲染时按层拉伸，剖切时只画目标层，成本低、来源广（CAD、PDF 平面图、手工描点都能产出）。
2. **竖向连接单独建表**。楼梯、电梯、扶梯是跨层寻路的唯一通道，必须显式声明 `to` 楼层，否则跨层路线会出现「穿墙上升」。
3. **坐标系可本地化**。`local-meters` + `origin` 让校园数据保持小整数，同时能反算经纬度做地图叠加与深链。

### 2.3 工具链

- `campus-import osm`：从 OSM 抽建筑轮廓，粗过滤 + 人工确认，产出 L1。
- `campus-import dxf|pdf`：从平面图抽轮廓（先只支持「描点 + 吸附」的半自动），产出 L2，人工补房间名。
- `campus-blender-export`：Blender 里参数化建模 → 导出 glb + 回写 `levels` 高度，双份一致。
- `campus-validate`：几何自检（多边形闭合、面积合理、楼层不重叠）、拓扑自检（每个房间可达、每个楼梯有双向边）、命名自检（id 唯一、小写连字符）。
- `campus-bundle`：压缩、切片、生成 `manifest.json` 与校验和，产出离线包。

`campus-validate` 的检查项**同时**写成测试用例，数据一改 CI 就报红，这是「多人多 agent 并行改数据」的前提。

### 2.4 多校适配与许可

- 一个仓可以放多个包：`packs/usts-tianping/`、`packs/usts-jiangfeng/`，站点用 `?campus=` 或子路径切换。
- 代码 AGPL-3.0 或 MIT（待定）；数据 CC BY-SA 4.0；模型在包内单独标 `license` 与 `attribution` 字段，OSM 派生的必须署名 ODbL。
- 校名、logo 不进数据层（`branding.json` 可选），避免 fork 的人被绑死在一所学校的视觉上。

## 3. 产品形态与客户端

### 3.1 四个入口

| 入口 | 用户意图 | 第一屏回答 |
|---|---|---|
| 地图 | 我在哪，怎么去 | 3D 全景 + 搜索 + 「我的位置」 |
| 信息 | 这栋楼/这间房有什么 | 地点详情：活动、通知、开放时间、评价 |
| 活动 | 最近有什么可去 | 时间轴卡片流，每张卡带地点与「导航」按钮 |
| 编辑器 | 数据怎么补 | 分步表单 + 平面图画布 |

StuDev 的四入口（课表/地图/知识/搜索/AI）里，前三个我们换成 地图/信息/活动，第四个换成 编辑器 + 搜索（端侧）。

### 3.2 PWA 先行，原生后置

先做 PWA 的三条理由：一套代码、可安装、Service Worker 天然支持离线包。原生壳只在三种需求成立时才做：后台定位与息屏语音导航、AR 相机、桌面小组件。届时优先用 Capacitor 包一层复用 Web 代码，而不是双端重写。

客户端能承担的重活（按投入产出排序）：

1. 离线包（整校 3D + 室内 + 路网，预估 8–20MB），地铁里也能查到教室。
2. 息屏语音导航（Web Speech + Wake Lock，或壳内原生 TTS）。
3. 扫码直达：二维码 → 深链 → 直接开会话。
4. AR 指路（后置，WebXR 或原生 ARCore，定位精度不足时只做「大致方向」）。
5. 桌面小组件：下一场活动 + 走过去几分钟。

### 3.3 状态与本地优先

选中的校园、主题、收藏地点、离线包版本全部存本地（localStorage / IndexedDB）。服务器不接收位置轨迹。这条既是隐私立场，也是省成本的手段：没有账号系统就没有账号系统的一切麻烦。

## 4. 地图：3D / 2D / 室内

### 4.1 双渲染同源

抽一个渲染无关的 `ViewState`：`{ campus, center, zoom, bearing, selectedId, level, mode }`。3D 渲染器（Three.js）与 2D 渲染器（Canvas 或 MapLibre）都订阅它，切换时保持语义一致：

- 切换不重置视角：把 2D 的 `center + zoom` 与 3D 的 `target + cameraHeight` 互相换算。
- 选中不丢：楼层剖切状态下切到 2D，自动展开为「该楼该层平面图」。
- 路线不重算：寻路在数据层完成，两个渲染器只是画同一条 polyline。

2D 不是降级版，而是另一种读法：看校园关系、看活动分布密度、看施工封路，2D 比 3D 清楚。默认给 3D，`Tab` 或手势切 2D，状态记住。

### 4.2 室内模型

进入一栋楼后自动进入三层结构：**楼体 → 楼层 → 房间**。

- 楼层剖切：默认只显示选中层 + 上一层的外壳（半透明），其余层隐藏。左侧楼层条可滑动，键鼠 `[` `]` 切换。
- 房间状态色：空闲（翡翠绿）/ 有活动（浅灰）/ 施工（条纹）/ 收藏（琥珀描边），沿用 StuDev 的语义，不新造色。
- 房间卡片：名称、容量、类型、当前活动、走到这里的分钟数、收藏。
- 竖向连接：楼梯电梯在剖面上画为竖井，点击直达目标层并高亮出口。
- 数据缺口可见：没建模的楼层显式显示「未建模 · 帮我补」，点进去就是编辑器，把维护成本转成数据来源。

### 4.3 导航内核

一期不做室内定位（ibeacon/UWB 成本与精度都不划算），只做**路线规划**：

- 室外用 `roadNetwork` 上图搜索（A*，欧氏距离启发的可采纳版本），现状已有 39 节点 / 42 段，需扩到覆盖教学楼、食堂、宿舍、体育馆、四个门。
- 室内用 `indoorNetwork`，楼层内边 + 竖向连接边。跨楼跨层查询：起点「房间 A / 3F」→ 终点「房间 B / 1F」，先解到出入口节点，再解室外段，再入户。
- 代价函数：距离 + 楼梯惩罚 + 无障碍模式下的台阶惩罚 + 施工封路（动态层）。
- 偏航重算：只在「位置漂移 > 25m」时重算，避免 GPS 抖动导致路线反复跳。
- 语音提示点：转弯前 15m、进门、上楼、到达，四条模板句足够。

### 4.4 性能预算

| 项 | 上限 | 说明 |
|---|---|---|
| 首屏可交互 | 3.0s（4G） | 3D 延迟加载，先出 2D 底图 |
| 三角面总数 | 40 万 | 单栋楼 LOD1 上限 3000 面 |
| 静态包 | 校园 3D 12MB / 室内 6MB | 切片 + Draco 压缩 |
| 帧率 | 中端机 30fps | 掉帧时自动降 LOD 与关阴影 |
| 寻路响应 | 200ms（跨楼跨层） | 预计算 + 内存图 |

性能预算写进 CI：`npm run size` 超限即失败，避免「加了个模型整体变卡」的慢性病。

## 5. 地点级信息与活动

### 5.1 数据模型

```jsonc
// place：静态地点，来自 campus pack
{ "id": "b-lib/r-301", "campus": "usts-tianping", "kind": "room|building|spot" }

// post：地点级内容，可长期存在
{ "id": "pst_01", "placeId": "b-lib/r-301", "kind": "notice|tip|lost|construction",
  "title": "三楼自习室周末延长到 23:00", "body": "...",
  "author": "anon|org_xx", "createdAt": "...", "expiresAt": "...",
  "status": "published|pending|reported|archived" }

// event：有起止时间的活动
{ "id": "evt_01", "placeId": "b-gym/court-1", "title": "社团招新",
  "start": "2026-11-21T14:00+08:00", "end": "2026-11-21T17:00+08:00",
  "organizer": "org_xx", "capacity": 200, "signup": "external|inline",
  "coverKey": "r2://...", "status": "published" }
```

两个关键约束：

1. **必须有 `placeId`**，且 `placeId` 必须能在当前校园包里解出坐标。发布时即校验，指不到地点的内容不允许存在 —— 这是「一键导航」成立的前提。
2. **必须有时间边界**。`event` 有起止，`post` 有 `expiresAt` 或默认 90 天。过期的自动归档，不做永久的僵尸信息流。

### 5.2 发布与治理

分三档，按成本递增：

- 白名单组织者（社团、学院）：直接发布，事后抽查。
- 认证学生：发布进 `pending`，由任意两名白名单成员或一名管理员确认。
- 匿名：只能发 `tip` 与 `lost` 两类，一律待审，且限频率（每设备每天 3 条）。

治理必备件：举报入口、下架理由、操作日志、「本条信息由 XX 发布，与校方无关」的免责标注。UGC 是这套系统最大的风险面，宁可先做成「只有社团能发」，等有人用再放开。

### 5.3 一键导航深链

统一格式：

```
https://map.mioc.cc/go?c=usts-tianping&p=b-lib/r-301&e=evt_01&from=me
```

- `p` 指向地点，`e` 可选带活动（打开后活动卡显示在路线卡上方）。
- `from=me` 表示「从我当前位置出发」，缺省则只做定位展示不启动导航（避免在群里点开就被要求授权定位）。
- 短链：`https://map.mioc.cc/g/ab12cd` 由服务端映射到长链，方便贴群里与做二维码。
- 微信内打开：直接可用 Web 版；检测到在微信内时提示「右上角 → 在浏览器打开」以启用定位与离线包。
- 兜底：如果 `p` 在旧包里不存在（数据已改），降级到楼栋级别并提示「房间已调整」。

分享入口做三处：地点详情页「分享」、活动卡「分享」、编辑器「生成二维码」。

### 5.4 时效与归档

活动结束后 24h 内转为「已结束」，保留 30 天供回看；地点级 `notice` 过期即隐藏但可查；所有归档数据不进首屏、不占搜索权重。信息流排序只用三个因子：时间临近度、地点关注度（收藏/到访）、组织者权重。不做个性化推荐的黑箱。

## 6. UI 设计规范（照 StuDev 那套）

### 6.1 六条原则

1. **数据密度优先**。一屏能看的信息量比留白重要，标杆是课表格子的密度，不是落地页的密度。
2. **状态色克制**。只保留四组语义色：翡翠绿=空闲/可达、琥珀=收藏/提醒、灰=占用/禁用、暖红=告警/封路。配色不用于装饰。
3. **地图永久占据主视区**，面板浮在地图上，可收起。绝不做「先看一个大标题再进地图」的落地页流程。
4. **时间刻度尺**是标志性控件：横向时间轴拨动即切换状态（空教室、活动时段、施工时段）。
5. **深浅双主题**，首屏前内联脚本回放，零闪白。
6. **零装饰动效**。只允许三种过渡：面板滑入、楼层剖切、路线绘制。

### 6.2 色与状态语义

| 语义 | 浅色 | 深色 | 用在哪 |
|---|---|---|---|
| 空闲 / 可用 | `#0f766e` 系 | 提亮一档 | 空教室、可通行 |
| 收藏 / 提醒 | `#b8791a` | 提亮 | 收藏地点、即将开始 |
| 占用 / 禁用 | 中性灰 | 中性灰 | 上课中、已满 |
| 告警 / 封路 | 暖红 | 提亮 | 施工、故障 |
| 选中 | 暖调底（不死蓝） | 暖调底 | 卡片与房间描边 |

沿用现有 landing 主题令牌（`--surface*`、`--primary`、`--iso-*`），不新起一套设计系统；只把语义色补成上面这四组。

### 6.3 布局与密度

- 顶栏：校园切换 + 搜索 + 主题 + 三入口（地图/活动/信息）。高度 48px，不做大 banner。
- 左栏（桌面 ≥960px）：搜索 + 结果列表 + 筛选；地图占右侧剩余全部。窄屏时左栏变成底部抽屉，三档高度可拖。
- 地图浮层：右下角 3D/2D 切换与楼层条；左下角比例尺 + 图例；右上角「回到我的位置」。
- 地点详情卡：宽 320px，最多 4 个区块（概览 / 活动 / 提示 / 路线），超出折叠。
- 字号：正文 14px、次要 12px、标题 16/20px，行高 1.5。中文不用小于 12px。

### 6.4 深浅主题与无障碍

- 两套令牌同表（light / dark），`prefers-color-scheme` + 本地覆盖。
- 对比度：正文 ≥ 4.5:1，大字号 ≥ 3:1；地图上的文字加半透明底衬。
- 触屏：点击区 ≥ 44px，`touch-action: manipulation`，禁双击缩放与 300ms 延迟。
- 键盘：`/` 聚焦搜索、`[` `]` 切楼层、`1/2` 切 3D/2D、`Esc` 关面板。
- 无障碍模式：路线避开台阶，语音提示带方向词与距离。

## 7. 技术架构

### 7.1 分层

| 层 | 选型 | 理由 |
|---|---|---|
| 构建 | Vite + TypeScript（strict） | 现有底座，冷启动快 |
| 3D | Three.js（WebGL2）+ 自实现剖切 | 不引 R3F，避免 React 依赖进入渲染核心 |
| 2D | Canvas 2D 自定义绘制（备选 MapLibre） | 自绘可控、无需瓦片服务 |
| 状态 | 一个轻量 store（~100 行，无依赖） | `ViewState` 不复杂，不需 zustand 类库 |
| 寻路 | 自写 A*（TS，纯函数） | 可测、可移植、可跑在 Worker |
| 后端 | Cloudflare Workers + D1 + R2 | 免运维、免费额度够、和 docs 站同一套经验 |
| 前端托管 | GitHub Pages（现有） | 不动 |
| 离线 | Service Worker + IndexedDB 缓存包 | 复用 docs 站 SW 经验 |

### 7.2 代码结构（目标形态）

```
src/
  core/           # 无框架纯逻辑：几何、寻路、视图状态、校验
    view/state.ts
    nav/astar.ts  nav/crossBuilding.ts
    geo/polygon.ts
  render/
    three/  scene.ts  slice.ts  lods.ts
    two/    canvas.ts  symbols.ts
  features/
    map/  info/  events/  editor/  share/
  data/           # 类型 + loader + schema 校验入口
packs/            # 多校数据包（每个子目录一个校园）
  usts-tianping/  campus.json  buildings/  indoor/  assets/
packages/
  campus-cli/     # import / validate / bundle 三个命令
```

关键约束：`core/` 不 import Three.js，也不 import DOM。这样寻路与几何能 100% 跑在 Node 里单测，也方便未来搬到原生壳。

### 7.3 后端极简设计

只做四件事：

1. `GET /api/pack/:campus/manifest` —— 包的版本与校验和（决定要不要更新离线包）。
2. `GET /api/feed?campus=&bbox=&from=&to=` —— 活动与帖子增量拉取。
3. `POST /api/post` / `POST /api/event` —— 发布（带 `placeId` 校验）。
4. `POST /api/report` + 管理端审核队列。

无账号体系；组织者用一次性邀请码换长期签名 key；签名 key 存 D1，权限只到「发布」。这些都用 Workers 做，冷启动与成本都近乎为零。

## 8. Agent 主导的开发工艺

核心问题：agent 产能高但容易跑偏，人时间少且不适合盯细节。解法是把「方向」与「验收」变成两个机械化接口。

### 8.1 六步流水线

| 步 | 谁做 | 产物 | 门禁 |
|---|---|---|---|
| 1 规格 | 人定方向，agent 写细节 | `docs/design/*.md` + `ADR-*.md` | 人读 1 页小结点头 |
| 2 切片 | agent | issue 清单（每个 ≤ 1 PR） | 每个切片带验收脚本名 |
| 3 契约 | agent | `*.test.ts` / schema / 类型（先红） | 测试必须能跑起来并失败 |
| 4 实现 | agent | 代码 + 数据 | 红→绿，不加无关改动 |
| 5 自检 | agent | CI 结果 + 截图 + 一句话结论 | 全绿才开 PR |
| 6 审人 | 小组成员 | 审核意见 / 合入 / 回退 | 分级规则见 8.3 |

铁律：**没有验收脚本的切片不准开工**。写不出脚本，说明需求还没想清。

### 8.2 切片模板

```
## 目标
一刷就能说清的单一行为（例：点击楼层条切层，剖切生效且相机不跳）

## 验收
- 单测：src/core/nav/__tests__/crossBuilding.test.ts 新增 N 条
- 视觉：截图 a11y/floor-3.png 与预期草图一致
- 数据：campus-validate 全绿

## 不做什么
不改相机控制器；不改 landing 页；不动其它楼层数据

## 风险
剖切与透明排序冲突，可能需两次渲染 pass
```

**「不做什么」比「做什么」重要**，它是防止 agent 顺手重构的唯一硬边界。

### 8.3 门禁分级（三色）

- **绿：可自动合入**。仅测试、文档、样式常量、数据补录（校验全绿）。agent 自审 + CI 绿即推。
- **黄：需一人看**。新增纯函数、UI 组件、单个页面。小组成员看三条：截图对不对、测试够不够、有没有偷改边界外的东西。
- **红：全体评审**。改 schema、改寻路算法、改渲染主循环、动部署与许可。必须提前一天发文档。

这样人每天只需处理 3–8 个黄/红条目，而不是读所有 diff。

### 8.4 并行与冲突

- 一个 agent 一次只拿一个切片，分支名 `feat/<切片号>`。
- 文件锁：切片声明自己会改哪些目录，重叠的串行。
- 数据并行：一栋楼一个人/一个 agent，文件名按楼栋 id 分，天然不冲突。
- 每早一个「同步点」：把绿条直接合，黄条排队，红条显式排期。

### 8.5 决策记录

任何「选 A 不选 B」都写 `docs/adr/NNN-标题.md`（背景 / 选项 / 结论 / 代价），一页以内。agent 下次接手先读 ADR，避免同一个坑反复讨论。

## 9. 建模精细化管理

模型是这类项目真正会烂掉的地方：不是写不出来，是三个月后没人知道那栋楼是谁拉的、多少面、对不对。

### 9.1 资产台账

`packs/<campus>/assets/registry.json`，每栋楼一条：

```jsonc
{ "buildingId": "b-lib", "source": "blender|osm|hand", "owner": "agent:model-3",
  "updatedAt": "2026-11-18", "lod": [1,2], "tris": 2480,
  "height": 24, "levels": 6, "materials": 4, "checksum": "sha256:...",
  "review": { "state": "approved|pending|rejected", "by": "member-b", "at": "..." } }
```

台账由 `campus-validate` 自动更新 checksum 与 tris，人只填 owner 与 review。缺台账的模型一律视为未完成。

### 9.2 建模规范

| 项 | 规范 |
|---|---|
| 单位 | 1 Blender unit = 1 米，场景原点 = 校园 `origin` |
| 朝向 | +X 东、+Y 北，无旋转（旋转在导出时烘入） |
| 命名 | `<buildingId>_<lod>.glb`，材质 `m_<语义>` |
| LOD | LOD1 ≤ 3000 面（远景）、LOD2 ≤ 12000 面（近景）、室内单独一份 `indoor.glb` |
| 层级 | 导出前必须与 `levels[]` 的 `elevation/height` 对齐，不得靠目测 |
| 原点 | 每栋楼原点在 footprint 中心、地面高度 |
| 贴图 | 只允许色块与程序材质，禁照片贴图（许可与体积双重原因） |

### 9.3 脚本化导出与校验

- `blender -b part.blend -P tools/export.py -- --check` 导出前自检：楼层数与数据一致、无游离顶点、无反向法线、总面数在预算内。
- 导出后 `campus-validate --assets` 再核一次（文件存在、体积、checksum）。
- 三视图截图自动生成（正/侧/顶），与实景照片一起作为 review 材料。
- 模型二进制走 Git LFS（或 R2 + 清单），仓里只留 `registry.json` 与校验和，避免仓体积失控。

### 9.4 审图流程

三层验收：几何对（轮廓与楼高对得上卫星图/实景）→ 结构对（楼层数、楼梯位置可走）→ 观感对（不丑、不穿模、LOD 切换不跳）。前两层看数据与截图，第三层才需要人看渲染。

### 9.5 分工看板

一栋楼一个 issue，标签 `model`、`indoor`；每个 agent 一次领 2–3 栋同类（教学楼一起、宿舍一起），好处是材质与楼层规律可复用，审图也成批。

## 10. 我的环境约束与优化

现状：2 vCPU / 1.6G 内存 / 40G 盘的 ECS，可用内存约 700MB。启一个 Vite dev server 尚可，跑 Vitest 全量尚可，跑 Playwright 或三端构建必死。

### 10.1 本机 vs 云端分工

| 工作 | 在哪跑 | 理由 |
|---|---|---|
| 写代码、改文档、生成 PDF | 本机 | 不吃内存 |
| 纯逻辑单测（core/） | 本机（tmux + 内存限额） | 全量 168 项约 44s |
| 类型检查 / lint | 本机 | 轻 |
| `npm run build` | 云端 | 本机曾 OOM |
| Playwright e2e / 截图 | 云端 | 本机无完整 chromium |
| 模型导出、批量 glb 压缩 | 云端 | 吃 CPU 与内存 |
| 离线包构建 | 云端 | 产出 artifact |
| 真机验证 | 人（手机） | 无法代劳，但可引导 |

### 10.2 四条具体改法

**一、把 CI 当“本地命令”用。** 定义 `ci/` 下的四个 workflow：`check`（typecheck+lint+unit）、`build`（构建 + 体积预算）、`visual`（Playwright 截图 + 像素 diff）、`pack`（离线包 + 模型校验）。本机只跑 `check`，其余用 `gh workflow run -f pr=...` 触发，告一段落用 `gh run view --log-failed` 拿结论。

**二、产物回传做视觉验收。** `visual` 产出截图 zip 作为 artifact，本机 `gh run download` 拿下来直接看图。这样即使本机没浏览器，也能用图像完成 UI 验收。

**三、内存硬约束写成习惯。** 本机任何构建放 tmux，外加 `systemd-run --scope -p MemoryMax=900M`；一次只跑一个；dev server 只看单页。

**四、Codespaces 走不通就用 Actions。** 现在 `gh codespace` 报 403，短期不指望；GH 托管 runner 免费额度（公开仓不限）里已经能拿到 7GB 内存与 4 核，足够跑构建与截图。需要更大时再考虑自建 runner（可在现有 ECS 上跑只做轻任务的 runner，重任务不上）。

### 10.3 视觉验收闭环

```
agent 改 UI → push 分支 → Actions 截图（light/dark × 960/1440 × 3 状态）
  → 像素 diff 超阈报警 → 人看 3 张关键图 → 一句话结论（可以 / 不行 + 哪不行）
```

截图基准（baseline）入仓，diff 阈值 0.3%；预期变更需在同一 PR 更新 baseline 并写一句说明。这样「UI 裂了」不再靠人肉抽查。

### 10.4 已知坑（写进 AGENTS.md）

- tmux 里 `pnpm`/`npm` 不在 PATH，先 `export PATH=/usr/local/bin:/usr/bin:/bin`。
- 本机 npm 官方源延迟高，用 npmmirror，偶尔 500 时回退官方源。
- 无完整 chromium，截图一律云端；本机 `systemd-run` 包 headless_shell 也建不出 WebGL。
- 构建包在 `systemd-run` 里会让 `dist/` 归属 root，干净验证前先清。
- 重活别和 gateway 抢内存，否则连回复都发不出去。

## 12. 风险与待拍板

| 风险 | 应对 |
|---|---|
| 室内数据靠人拉，进度不可控 | 先做 4 栋示范楼；「未建模」入口让用户自己补；编辑器降低门槛 |
| UGC 审核成本被低估 | 先只开白名单组织者；匿名只限失物与提示；预留举报与下架流程 |
| agent 改坏架构 | 三色门禁 + `core/` 无框架依赖 + ADR 记录 |
| CI 免费额度 | 缓存 node_modules 与构建产物；截图矩阵只跑关键页；公开仓额度宽裕 |
| 多校适配变成大工程 | 只通用数据层，前端只做「可配置」，不做多租户后台 |
| 许可 | 自有代码选 AGPL-3.0 或 MIT，OSM 派生数据必须 ODbL 署名，模型单独标 license |

需要拍板的五件事：

1. 代码许可选 AGPL-3.0 还是 MIT（影响别人能不能闭源拿去用）。
2. 原生壳要不要现在立项（Android Kotlin vs Capacitor 包一层）。
3. UGC 首发范围：只给社团，还是也开匿名失物。
4. 室内示范楼选哪四栋（建议：图书馆、一栋教学楼、食堂、体育馆）。
5. 通用化做到「数据规范 + CLI」为止，还是连 UI 也要做成换皮就能用。
